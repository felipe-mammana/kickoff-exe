================================================================
1. VISÃO GERAL
================================================================

O EXE Inventário TI é uma aplicação web desenvolvida em PHP e MySQL para cadastro, organização, consulta e documentação de ativos de tecnologia da informação.

Principais objetivos:
- cadastrar empresas;
- cadastrar dispositivos;
- relacionar equipamentos a empresas;
- controlar etiquetas e hostnames;
- registrar colaborador e departamento;
- armazenar informações técnicas;
- armazenar credenciais protegidas;
- anexar fotos;
- aplicar filtros;
- registrar auditoria;
- autenticar usuários;
- fornecer API REST;
- exportar dados e documentos.

Tecnologias principais:
- PHP;
- MySQL / MariaDB;
- HTML;
- CSS;
- JavaScript.

A aplicação não depende de um framework PHP completo. Ela utiliza uma arquitetura MVC própria.

30. CRIPTOGRAFIA DE CREDENCIAIS
================================================================

Campos protegidos:
- machine_password
- admin_password

Classe:
CredentialCrypto

Algoritmo:
AES-256-GCM

IV:
12 bytes

Authentication Tag:
16 bytes

AAD:
exe-kickoff:credential:v1

Prefixo:
enc:v1:

Formato:
enc:v1: + Base64(IV + TAG + CIPHERTEXT)

Derivação da chave:
hash('sha256', APP_KEY, true)

Comportamento:
- não criptografa novamente valor que já começa com enc:v1:;
- credencial inválida retorna [credencial invalida];
- APP_KEY ausente gera exceção.

55. POSSÍVEIS VULNERABILIDADES E RISCOS
================================================================

A análise abaixo é estática. Alguns itens são riscos arquiteturais e não necessariamente vulnerabilidades exploráveis sem teste prático.

------------------------------------------------------------
55.1. CONTROLE DE ACESSO A DISPOSITIVOS E EMPRESAS
PRIORIDADE: ALTA
------------------------------------------------------------

Problema:
qualquer usuário autenticado pode criar, editar, desativar equipamentos e remover fotos.

Somente o módulo de empresas exige admin.

Risco:
um usuário comum pode potencialmente alterar ou desativar equipamentos pertencentes a qualquer empresa existente.

Também não existe, no modelo atual, isolamento por empresa/tenant.

Impacto:
- Broken Access Control;
- risco de IDOR;
- alteração indevida de ativos;
- possível acesso a informações sensíveis.

Recomendação:
implementar permissões granulares.

Exemplo de modelo:
roles:
- admin
- technician
- viewer

E/ou:
user_company_permissions
- user_id
- company_id
- can_view
- can_edit
- can_delete
- can_export

Em todos os controllers e endpoints:
validar se o usuário possui acesso à empresa do equipamento.

------------------------------------------------------------
55.2. API COM SESSÃO SEM CSRF
PRIORIDADE: MÉDIA / ALTA
------------------------------------------------------------

Problema:
a API aceita autenticação por sessão web, mas as rotas POST/PUT/PATCH/DELETE não executam verify_csrf().

O cookie SameSite=Lax reduz o risco, mas não substitui uma política explícita.

Recomendação preferencial:
API deve aceitar apenas Bearer Token.

Alternativa:
se ApiAuth detectar autenticação por sessão:
- exigir X-CSRF-Token;
- validar o token da sessão.

------------------------------------------------------------
55.3. AUSÊNCIA DE RATE LIMITING
PRIORIDADE: ALTA
------------------------------------------------------------

Não foi identificado rate limiting:
- no login;
- na API;
- no uso de tokens.

Riscos:
- brute force;
- credential stuffing;
- abuso da API;
- DoS de aplicação.

Recomendação:
implementar limitação por:
- IP;
- usuário/e-mail;
- token;
- endpoint.

Exemplo:
login:
5 tentativas por 10 minutos por IP/e-mail.

API:
limites diferenciados por token.

Problema:

Recomendação:

Sugestão:

Também revisar compatibilidade com:

- fileinfo.

55.5. APP_DEBUG EM PRODUÇÃO
PRIORIDADE: MÉDIA
------------------------------------------------------------

Quando APP_DEBUG=true:
- erros são exibidos;
- API pode retornar mensagem real da exceção.

Risco:
vazamento de:
- caminhos;
- SQL;
- detalhes internos;
- nomes de arquivos;
- estrutura do sistema.

Recomendação:
produção:
APP_ENV=production
APP_DEBUG=false

Também:
- registrar erros apenas em logs;
- retornar mensagens genéricas ao cliente.

------------------------------------------------------------
55.6. CONFIGURAÇÃO DE EXEMPLO COM CREDENCIAIS FRACAS
PRIORIDADE: MÉDIA
------------------------------------------------------------

local.example.php contém:
- admin@empresa.com;
- senha "troque-esta-senha";
- root sem senha;
- APP_KEY de placeholder.

Não é vazamento real por si só, porém existe risco de implantação incorreta.

Recomendação:
na inicialização:
- impedir APP_KEY padrão;
- impedir ADMIN_PASSWORD padrão;
- impedir DB_PASS vazio em produção;
- emitir erro fatal se valores placeholder forem detectados.

------------------------------------------------------------
55.7. DESCRIPTOGRAFIA AUTOMÁTICA DE CREDENCIAIS
PRIORIDADE: MÉDIA
------------------------------------------------------------

Machine::find() e Machine::byCompany() retornam credenciais já descriptografadas.

Risco:
uma nova View, Controller ou exportação pode acidentalmente expor:
- machine_password;
- admin_password.

Recomendação:
não descriptografar automaticamente.

Criar métodos separados:
Machine::findPublic()
Machine::findWithCredentials()

Ou:
decryptCredentials() apenas quando explicitamente solicitado e autorizado.

Também:
registrar auditoria específica quando uma credencial for visualizada.

------------------------------------------------------------
55.8. AUSÊNCIA DE CSP
PRIORIDADE: BAIXA / MÉDIA
------------------------------------------------------------

Headers atuais são bons, mas não existe Content-Security-Policy.

Recomendação inicial:
Content-Security-Policy:
default-src 'self';
img-src 'self' data:;
style-src 'self';
script-src 'self';
frame-ancestors 'self';

A política final precisa considerar os assets reais usados pelo frontend.

------------------------------------------------------------
55.9. AUDITORIA PODE FALHAR SILENCIOSAMENTE
PRIORIDADE: BAIXA / MÉDIA
------------------------------------------------------------

AuditLog::record() captura exceção e continua.

Ponto positivo:
não derruba a operação.

Risco:
alterações podem ocorrer sem histórico se a auditoria estiver quebrada.

Recomendação:
- log separado;
- alertas;
- monitoramento;
- health check;
- fila/retry opcional;
- métrica de falhas de auditoria.

------------------------------------------------------------
55.10. ISOLAMENTO MULTIEMPRESA
PRIORIDADE: ALTA SE O SISTEMA FOR MULTITENANT
------------------------------------------------------------

Atualmente:
usuário autenticado vê e atua sobre empresas disponíveis.

Se o sistema for usado por clientes diferentes:
isso deve ser corrigido antes.

Recomendação:
associação explícita:
users <-> companies

E validação em:
- DashboardController;
- MachineController;
- CompanyController;
- ApiV1Controller;
- ExportController.

------------------------------------------------------------
55.11. CONTROLE DE EXPORTAÇÃO
PRIORIDADE: MÉDIA
------------------------------------------------------------

Atualmente usuários comuns podem exportar dispositivos.

Recomendação:

can_export_devices

Também:
- limitar exportação à empresa autorizada;
- auditar quem exportou;
- considerar mascarar IPs/hostnames dependendo do perfil.

------------------------------------------------------------
55.12. VISUALIZAÇÃO DE CREDENCIAIS
PRIORIDADE: MÉDIA
------------------------------------------------------------

O sistema criptografa credenciais corretamente, porém a política de visualização precisa ser endurecida.

Recomendação:

- registrar evento credential_viewed;
- não carregar senha na página por padrão;
- opcionalmente exigir reautenticação.

------------------------------------------------------------
55.13. HEADERS ADICIONAIS
PRIORIDADE: BAIXA
------------------------------------------------------------

Recomendações:

- Permissions-Policy;
- Strict-Transport-Security em HTTPS;
- Cache-Control adequado em páginas sensíveis.

Exemplo:
Strict-Transport-Security: max-age=31536000; includeSubDomains

Usar somente depois de confirmar HTTPS permanente.

------------------------------------------------------------
55.14. POLÍTICA DE SENHA

Não foi identificado mecanismo completo de:

Recomendação:

55.15. LOGS DE AUTENTICAÇÃO

Melhorias:

- alerta para muitas tentativas;
- não armazenar dados sensíveis além do necessário.

64. RESUMO FINAL
================================================================

O projeto possui uma base técnica boa para um sistema PHP sem framework.

Pontos fortes:
- arquitetura organizada;
- separação de responsabilidades;
- prepared statements;
- autenticação com hash;
- CSRF na web;
- sessões endurecidas;
- auditoria;
- criptografia AES-256-GCM;
- API versionada;
- tokens com hash;
- uploads validados;
- soft delete;
- exportações;
- headers básicos de segurança.

Principais pontos a corrigir antes de um uso corporativo mais amplo:
1. autorização granular;
2. isolamento entre empresas;
3. rate limiting;
4. política correta de sessão/API;
5. atualização de PHP;
6. proteção adicional de credenciais;
7. hardening de produção;
8. CSP e monitoramento.

Conclusão:
a aplicação já possui várias boas práticas de segurança, mas o maior risco atual não está em SQL Injection ou upload de PHP; está principalmente em controle de acesso e autorização entre usuários, empresas e dispositivos.
